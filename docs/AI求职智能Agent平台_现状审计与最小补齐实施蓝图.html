1事实基线：当前项目到底是什么

以下内容来自 GitHub 主仓库，不来自聊天导出压缩包。任何后续改造都必须先承认这条真实基线。

仓库定位

当前项目是一个 local-first、合规边界明确的个人岗位筛选辅助工具：Userscript 读取用户主动浏览页面的可见 DOM，后端基于 Spring Boot 完成规则信息接收、Redis 缓存、Profile RAG-Lite、DeepSeek 分析、MySQL 持久化和反馈保存。

BOSS 可见 DOM→ Userscript→ POST /api/job/analyze→ Redis Cache→ Profile RAG-Lite→ DeepSeek→ MySQL→ 反馈
已实现

后端主体

Spring Boot 3 / Java 17，Controller、Service、Repository、DTO 和配置已存在。

已实现

缓存与持久化

Redis 缓存最终岗位分析 Response；MySQL 保存岗位、分析、画像、Chunk 和反馈。

轻量版本

RAG 与 Tool

RAG 当前为关键词 Top-K；Tool 当前主要是业务能力概念化封装，不是模型自主 Function Calling。

禁止误判：当前项目不是“只有油猴脚本”，但也不是已经完成 Embedding、标准 Tool Registry、节点级 Trace、复杂意图路由和可恢复状态机的成熟 Agent 平台。

当前代码已能支持的真实面试口径

  • 为什么需要 Spring Boot 后端：隐藏 Key、访问画像、缓存、持久化、调用模型和校验输出。
  • Redis 用途：同一 profileVersion + 同一 JD 复用最终结果；Redis 失败绕过缓存。
  • Profile Memory：用户画像、历史结果和反馈持久化；reindex 后生成新的 profileVersion。
  • RAG-Lite：按画像字段构建 Chunk，通过岗位查询词做关键词匹配，返回 Top-K 证据。
  • 结构化输出：Prompt 约束 JSON，Java 代码校验枚举、分数范围、必填字段和列表字段。
  • 异常降级：模型未启用、无 Key、请求/解析异常时使用规则结果生成 Fallback。

5最小改造原则：少工程化，但不能失控

必须坚持

  • 复用现有主链：不重写 Controller、缓存、Repository、Fallback。
  • 唯一编排入口：最多一个 AgentWorkflowService，禁止同时新增 Orchestrator、Coordinator、Manager 等重复类。
  • 每批可独立运行：某个新能力关闭后，原岗位分析仍可运行。
  • 新增能力有开关：Embedding、Tool Calling、Trace 都应有配置或安全降级。
  • 先跑通再美化：先使用 MySQL JSON/文本存向量，不引入专用向量数据库。
  • 每个节点有证据：日志、数据库行、接口返回三者至少有一个可观察证据。

明确不要做

  • 不引入 LangGraph、Dify、Coze 或复杂工作流框架。
  • 不拆微服务，不引入消息队列和分布式任务调度。
  • 不做多 Agent 协作、无限 ReAct 循环、复杂 Planner。
  • 不做 Milvus/ES 集群、Embedding 微调或 Rerank 平台。
  • 不做生产级中断续跑、事件溯源、分布式锁。
  • 不保存模型隐藏思考链；Trace 只记录可观察执行信息。
工程化最低线：虽然不追求复杂架构，但必须明确唯一主入口、上下文、数据落点、异常降级和验收标准。否则 Vibe Coding 会制造重复职责和前后不一致。

实现方式

不要把现有业务全部复制到新 Service。AgentWorkflowService 只负责创建 Context、按节点调用现有能力、更新 Task； WorkflowNodeRunner 用统一模板记录开始时间、结果摘要、异常和耗时。 

// 伪代码，仅表达设计，不要求照抄
return nodeRunner.run(context, AgentNode.RAG_RETRIEVED,
    () -> userProfileRagService.searchDefaultProfile(query, topK),
    result -> "chunks=" + result.chunks().size());

缓存命中规则

每次请求仍应有当前 taskId。缓存命中时记录 CACHE_CHECKED = HIT，返回缓存中的业务分析内容，但不要把历史 taskId 当成当前任务。

异常原则

  • Redis失败：节点标记降级，但继续后续步骤。
  • Embedding失败：RAG节点成功但标记 KEYWORD_FALLBACK。
  • LLM失败：记录错误，进入 Fallback；最终任务可标记 COMPLETED_WITH_FALLBACK。
  • 数据库核心保存失败：任务标记 FAILED，返回明确错误，不假装成功。
  • Trace自身写入失败：只记录日志，不阻断主业务。

最小查询接口

GET /api/trace/{taskId}
返回：任务摘要 + 按时间排序的节点列表

最小调用循环：最多两轮

第1次模型调用：携带 tools 和 tool_choice=auto
    ↓
模型返回 0~N 个 tool_calls
    ↓
ToolRegistry 检查名称 → Schema校验参数 → ToolExecutor 执行
    ↓
将 assistant tool_calls 与 role=tool 的结果追加到 messages
    ↓
第2次模型调用：基于工具结果生成最终结构化分析
    ↓
停止，不做无限循环

DeepSeek 官方 Chat Completion 支持 OpenAI-compatible Tool Calls。优先使用原生 tools、tool_calls 和 role=tool 协议；如果当前模型/配置不支持，则允许通过配置切回固定 Workflow + 直接 Service 调用，但必须在 Trace 标记调用模式。

参数校验与安全

  • Tool名称必须在 Registry 白名单中，不存在则拒绝。
  • 参数按 JSON Schema 校验；缺失关键字段返回结构化错误给模型，最多修正一次。
  • feedbackTool 属于写操作，必须由用户明确确认或传入 confirmed=true；模型不能自行写反馈。
  • 不提供删除数据库、执行任意SQL、文件系统或Shell Tool。
  • 多个只读Tool可顺序执行；第一版不追求并行。

接口策略

保留：POST /api/job/analyze  // Userscript固定岗位分析
新增可选：POST /api/agent/execute
请求：{ userInput, jobRequest?, confirmedAction? }
返回：{ taskId, intent, answer/result, toolCalls, traceSummary }

10批次4：正式 Schema 校验 + 反馈更新 Memory

校验链

失败：使用“修复结构Prompt”重试1次
仍失败：进入现有fallbackAnalyze()
Trace标记：SUCCESS / REPAIRED / FALLBACK

Memory 最小更新

现有画像、Chunk、profileVersion和反馈表已经构成长时记忆基础，只补自动更新触发：

保存 job_feedback
    → transaction提交成功
    → 标记 profile_index_dirty = true（推荐）
       或个人数据量小时直接 reindexDefaultProfile(true)
    → 下次分析前检查dirty并重建
    → profileVersion变化
    → Redis旧Key自然失效

避免过度实现

  • 不做技能自动衰减、冲突记忆合并、RLHF或在线学习。
  • 旧求职目标与新目标冲突时，以当前 user_profile 为主，历史反馈仅作为证据，不覆盖主画像。
  • 同公司不同岗位通过 job_record_id 区分反馈，不按公司名合并。
